# Importing MusicXML and LilyPond into VexTab

Build two readers and one writer that produces editable VexTab grammar v2. Start with measured Western staff notation, then qualify piano, voices and lyrics, fretted instruments, percussion, and ensemble scores. A musician should be able to import a piece, open the result in an ordinary VexTab editor, change a note, and print or play the revision. A caller should also be able to convert a file in Node or a browser worker without installing an engraver.

Ship the readers in a **separate npm package**, provisionally `vextab-import`, with one entry point per format. Use MusicXML to establish the measure and voice model. Build the LilyPond reader alongside it as soon as both can use the same writer. MusicXML encodes the contents of a score. LilyPond describes how to construct one, and can call Scheme while doing so. Only the resolution of musical events and their translation into VexTab should be shared. [MusicXML 4.0](https://www.w3.org/2021/06/musicxml40/) · [LilyPond notation reference](https://lilypond.org/doc/v2.26/Documentation/notation/)

## What the output must preserve

Consider two quarter notes in G major, F sharp followed by F natural. A second voice enters on middle C with the natural. In MusicXML with one division per quarter, voice 1 has two notes of duration 1. A backup of 1 returns the cursor to the second beat, where voice 2 has its first note. In LilyPond the same measure can be written as follows.

```lilypond
\new Staff {
  \key g \major \time 2/4
  << { fis'4 f' } \\ { s4 c' } >>
}
```

Both imports should produce music equivalent to this runnable output.

```vextab2
meter 2/4
staff {
  key G
  voice upper { :q F#4 Fn4 | }
  voice lower { :q skip C4 | }
}
```

The skip puts C4 at exactly 1/4 of a whole note without printing a rest. Both F natural and C sound at that onset. In G major an unqualified VexTab `F4` takes the sharp from the key, so the writer must spell the natural explicitly. In MusicXML a missing pitch alteration means zero. In LilyPond the written pitch name supplies the alteration independently of the key. The accidental a musician sees, including a courtesy sign, is a separate decision. Check the projected pitches as well as the text. [VexTab pitch projection](../src/score/grammar2/project.ts) · [MusicXML pitch](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/pitch/) · [LilyPond pitches](https://lilypond.org/doc/v2.26/Documentation/notation/writing-pitches)

## Package and conversion contract

| Proposed entry | Responsibility and cost |
| --- | --- |
| `vextab-import/musicxml` | Read plain XML text or bytes. Use one event-driven XML reader in Node and browsers. Handle XML encoding before tokenization when given bytes. |
| `vextab-import/mxl` | Accept archive bytes, locate and decompress the selected score, then call the same XML reader. Only this entry needs ZIP support. |
| `vextab-import/lilypond` | Read a source string and an optional map of named include files. Carry filenames through diagnostics. |
| Optional CLI in the importer package | Adapt files or stdin to the same functions. Write VexTab to stdout or a named output, diagnostics to stderr or JSON. Multiple movements require selection or an explicit output directory. |

Expose typed functions such as `importMusicXML(input, options)` and `importLilyPond(input, options)`. Return a discriminated result with status (`exact`, `partial`, or `failed`), target grammar/version, diagnostics, and, on success, a list of documents with title, source selection and VexTab text. “Exact” applies to the declared musical and notation profile. List source-only presentation changes separately. Offer strict conversion by default. A caller can request partial output for **known, located losses**. An unresolved music expression with unknown timing blocks its dependent score in either mode. Independent movements may still succeed, with per-movement status. Avoid a single success flag that conflates all three cases.

Each diagnostic carries a stable code, severity, source file or archive member, source range, part/measure/voice when known, affected musical fact, and the action taken. Offer an optional map from generated UTF-16 text ranges to input ranges. Preserve both definition and use sites for LilyPond variables. A MusicXML chord assembled from several elements can map to several ranges. Keep mapping data outside the emitted music. Source maps refer to a specific revision of each file. Escape literal text with the target grammar's quoting rules, and assign deterministic, collision-free identifiers while keeping the original display names.

Keep the importer in a sibling package directory with its own manifest, declarations, tests and pack list. The existing package depends on VexFlow and its public parser module also imports VexFlow. Use `vextab/parse` in development and consumer tests, or as an explicitly supplied validator. Keep production conversion independent of VexFlow, DOM, fonts, audio and the legacy parser. Declare the minimum compatible VexTab version for each target profile. A score requiring a future spelling must select that profile explicitly. Subpath exports isolate download and execution costs for bundled applications. npm still installs the contents and regular dependencies of the package. Measure packed and installed bytes in M0. Split the XML, ZIP or LilyPond adapter into its own npm package if its install cost warrants it, while keeping the writer private to the importer family. An npm dependency from VexTab back to its importer would defeat the package split. ### Shared musical model and writer

1. **Read in source order.** The XML reader can discard element content when it completes a measure, retaining active state, unresolved references and normalized music. The LilyPond reader needs a syntax tree for scoped definitions and reusable expressions. Put input limits on both readers. Keep source slices by offset instead of copying text into every event.
2. **Resolve written time.** Store reduced rational numbers in whole-note units for measure extent, onset, and elapsed duration. Retain the written base value, dots, tuplet ratios and any performance offset separately. Use bounded integer arithmetic through comparison and emission. Each voice has a clock. Distinguish attacks, chord heads, visible rests, silent skips, grace events, and zero-time directions. Carry source measure labels separately from the written measure index, including pickups and irregular bars.
3. **Resolve identity.** An event belongs to a part and voice and can print on another staff. Keep ordered heads with written step, octave and alteration, desired sign, sounding interval, percussion identity, or string/fret/tuning. Store key, clef, meter, instrument and tempo changes at a staff/part and rational time. Store spans as typed pairs of event/head or time anchors. Keep repeat bodies and alternative paths with their written measures. Derive performed visits separately.
4. **Write VexTab.** Use a small typed writer for headers, parts, named voices, bars, notes, head/event attachments and spans. Use one readable voice sequence, stable head order, explicit changes of duration and short lines at bar boundaries. Keep original part order. Insert skips only for known silent time. Use nested VexTab blocks for properly nested spans. Crossing spans require independent endpoints or a loss diagnostic. Resolve ties by pitch and head identity across bars, including a chord with just one sustained head. Check generated byte, token and expanded-event counts against the selected target profile before reporting success.
5. **Validate the public artifact.** Parse the emitted text with the target package in CI. Project it to notation and playback and compare musical facts with independently established expectations. Reuse VexTab's exact-time conventions and data types where they fit. Keep the private input model small and extensible. Directly constructing a `ScoreV2` would bypass text parsing and give editor ranges in the wrong document. The existing migration script is a precedent for emitting and reparsing text. ## MusicXML reader

Use the 4.0 Final Community Group Report as the normative profile. Qualify common 3.1 exports separately, then add older exporter/version pairs when a fixture demonstrates the need. Record the declared version and exporter. Tag 4.1 draft constructs individually. A filename extension or a successful XML parse says little about musical coverage. [4.0 specification and schemas](https://www.w3.org/2021/06/musicxml40/) · [4.1 draft](https://musicxml.formats.music/)

| Source feature | Import rule and acceptance case |
| --- | --- |
| Partwise, timewise and MXL | Read the part list, names, instrument IDs and score order first. Normalize either root to indexed part/measure records. In MXL follow the first rootfile path in `META-INF/container.xml` even when a preview or other resource appears first in the archive. Identify an opus explicitly and require movement selection when supported. Test UTF-8 and UTF-16. Accept ordinary historical DOCTYPE declarations without loading remote DTDs. Limit archive entries, expanded bytes and XML depth. [Structure](https://www.w3.org/2021/06/musicxml40/tutorial/structure-of-musicxml-files/) · [MXL containers](https://www.w3.org/2021/06/musicxml40/tutorial/compressed-mxl-files/) |
| Measure time and simultaneity | Keep a document cursor per part-measure. Convert duration to whole notes as `duration / (4 × divisions)` with the divisions active at that position. `backup` and `forward` move the cursor. Track the maximum extent. A chord member takes the previous attack's onset without advancing the cursor and may end earlier. Grace notes take no ordinary cursor duration. Cue notes can consume time. Keep explicit voice IDs, resolve omitted IDs conservatively and distinguish voice ownership from staff placement. A partial backup need not return to the barline. [Chord rules](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/chord/) · [Backup](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/backup/) |
| Written value and sounding time | Read type, dots, beams and tuplet brackets separately from elapsed duration. `time-modification` can encode a cumulative ratio across nested tuplets. Resolve individual bracket spans before applying ratios once. Derive a missing type only when justified, and report ambiguous spellings. Invisible rests still consume their elapsed time. Keep grace stealing/make-time, attack/release adjustments and cue playback as separate performance facts. [Time modification](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/time-modification/) · [Note](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/note/) |
| Pitch, instruments and staves | Keep written spelling and optional accidental glyph, including cautionaries. Apply the active instrument transposition once to obtain sounding pitch. Read per-staff attributes in musical time order even when another voice is serialized later. Map unpitched display position and instrument/MIDI identity separately. TAB string 1 is highest while staff-tuning line numbers start at the bottom. Verify tuning, capo and explicit fret against sounding pitch. Pair notation and TAB copies only with evidence of matching events and provenance. Preserve ambiguity for review. [Attributes](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/attributes/) · [Tablature](https://www.w3.org/2021/06/musicxml40/tutorial/tablature/) · [Percussion](https://www.w3.org/2021/06/musicxml40/tutorial/percussion/) |
| Directions, spans and form | Place directions, harmony and figured bass at their offset from the current cursor with their staff/voice scope. Index numbered start/continue/stop elements by kind and scope. Match in musical order, accounting for cross-staff spans and reused numbers. Preserve a sounding `tie` separately from a printed `tied`. Keep lyric verse, syllabic role, elision and extenders. Read barlines, repeats, ending pass numbers, rehearsal signs, and sound/navigation directives before computing visits. [Directions](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/direction/) · [Spanner ordering](https://www.w3.org/2021/06/musicxml40/musicxml-reference/data-types/start-stop-continue/) · [Written ties](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/tied/) |

Prefer one maintained streaming XML parser with location support. Benchmark plain XML separately from ZIP extraction. Test a narrowly imported ZIP reader for stored and deflated entries with bounds enforced during inflation. A browser DOM prototype can establish expected output for small scores. A full DOM, a MusicXML renderer, and runtime schema validation each add costs that the conversion contract can avoid. Keep XSD validation in the fixture tools.

## LilyPond reader

Target the static music constructs of **2.26**, with a separately tested **2.24** profile and selected older repertoire. Report the source's declared version and any compatibility assumption. Use a version-pinned native LilyPond executable as a test oracle. A native engine or a LilyPond → MusicXML bridge is a poor default for browser conversion because it adds a language runtime or an additional translation that can discard notation. Historical sources can be prepared with `convert-ly` in the test tooling. Pin the original and converted files and record any manual fixes. [LilyPond releases](https://lilypond.org/download.html) · [Usage manual](https://lilypond.org/doc/v2.26/Documentation/usage-big-page)

| Source feature | Import rule and acceptance case |
| --- | --- |
| Expressions, variables and includes | Tokenize with modes for notes, chords, lyrics, drums, markup, strings and comments. Parse sequential braces, simultaneous brackets, chord brackets and command arguments with source ranges. Resolve variable uses against scoped definitions in source order. Allow bounded expansion and an explicit virtual file map for includes. Detect missing files, cycles, excessive depth and repeated expansion. Identify books, bookparts and scores, including implicit scores. Select the printable movement when explicitly requested. Keep separate MIDI-only score blocks out of that selection. |
| Pitch and durations | Support absolute, fixed and relative entry, octave marks, language-specific note names (default Nederlands), and diatonic transposition with spelling. In relative mode choose the nearest diatonic octave ignoring accidentals, then apply explicit octave marks. Within a chord, resolve heads in sequence. The next note uses the chord's first pitch as its reference. Thus `\relative c' { <c e g>4 b }` ends on B3. Inherit omitted durations, starting at a quarter. Handle duration-only repeats and `q` chord repetition. Distinguish a written dot, `*n/m` scaling and a printed tuplet. [Pitch reference](https://lilypond.org/doc/v2.26/Documentation/notation/writing-pitches) · [Rhythm reference](https://lilypond.org/doc/v2.26/Documentation/notation/writing-rhythms) |
| Parallel music and context | Sequences add their lengths. Simultaneous branches share an origin and advance the enclosing expression by the longest branch. Resolve named and implicit contexts, explicit voice separators, shared global music and staff changes. Simultaneous expressions may combine a settings stream with notes in one context. Do not manufacture voices for the settings. Generate bars from timing, meter and `\partial`. Treat a vertical bar as a bar check and `\bar` as a printed barline. Preserve `r` rests, `s` skips, `R` full-measure rests and grace order. |
| Repeats and attachments | Preserve printed volta repeats and pass-specific alternatives. `\repeat unfold` creates written copies, while tremolo has its own timing and engraving. Resolve ties on individual chord heads, articulations, explicit beams, slurs, dynamics, hairpins, pedal and ottava. Link `\lyricsto` to the named voice before attaching syllables, hyphens and melismas. Give chord mode and figured bass their own rhythmic lanes. Map TabStaff string constraints and tuning, DrumStaff instruments, and PianoStaff voice changes before choosing any target spelling. |
| Properties, Scheme and unknown commands | Implement a table of known command signatures, modes, scope, duration effects and supported literal arguments. Handle common static properties and a small set of typed literals or named tunings. A recognized cosmetic override with known extent can be reported and omitted. An unknown music function can consume the next expression, generate notes or change the meter. Stop at that location if the meaning is undetermined. Arbitrary Scheme, embedded evaluators, custom engravers and filesystem search are outside the portable profile. [Extension language](https://lilypond.org/doc/v2.26/Documentation/extending-big-page) |

**A real compatibility test.** Mutopia's *Maple Leaf Rag* declares 2.14.2. Its print score references two variables, uses octave-dependent chords and moves one line onto the other staff. A second score uses a function to unfold repeats for MIDI. Import the selected **print score** once. Use the supplied MIDI file separately to check the first strain across both endings. Qualifying the whole original file requires recognizing or reporting its older property and markup syntax. Qualifying an excerpt or a converted fixture must say so in the results. [Mutopia source, PDF and MIDI](https://www.mutopiaproject.org/cgibin/piece-info.cgi?id=23) · [Existing first-strain comparator](../issues/199/check-joplin.py)

## Target features and ownership

VexTab 6.2.3 in this checkout pins VexFlow 5.9.0. Grammar v2 already has named voices, pickups, meter changes, a paired grand staff, nested tuplets, named head ties, lyrics, harmony, TAB gestures, custom drums and editions. Use those through the existing parser and projections. Track support in separate columns for **text, screen, print and playback**, with “inapplicable” available for visual-only features. A symbol visible on screen establishes little about its timing or its appearance across a printed system break. Simple headings, labels, system breaks and paper settings are worthwhile when their intent maps to an existing edition option. Give early music, chant, mensural scores and contemporary graphical notation their own future profiles. Keep their occurrences visible in corpus results.

### Verifying correctness

- **Start with paired micro-scores.** Hand-author the same music independently in both formats, a small table of expected events, and the expected VexTab. Include the two-voice example above, a tied chord with reordered heads, a transposing instrument and a pickup with a late voice. Compare reader output to the table, then reparse the emitted text and compare again. Check part/voice/staff, bar and rational onset, written and sounding pitch, elapsed duration, heads, spans and directions. Use text snapshots for readability and determinism. Two importers can share the same writer bug.
- **Use independent references.** For XML, validate relevant inputs offline with the pinned schema/catalog, then obtain a second musical reading for supported fields using music21. Preserve known nonconforming exporter samples as named compatibility cases. For trusted LilyPond fixtures, run a pinned native release with named staves and its event listener, then compare notes and durations. Its event files cover selected event kinds and may round time values. Use source-derived exact fractions for tuplets. Compare the written score first and normalized MIDI note-on/off tuples after repeats separately. MIDI loses enharmonic spelling, staff ownership, TAB position and most engraving. [MusicXML test tooling in music21](https://music21.org/music21docs/developerReference/musicxmlTest.html) · [LilyPond event listener](https://lilypond.org/doc/v2.26/Documentation/notation/saving-music-events-to-a-file)
- **Use existing independent counts carefully.** The Haydn comparator checks 772 principal attacks and rests across four parts in a 42-written-measure excerpt. It skips graces and an auxiliary voice. The Joplin comparator checks 552 performed note onsets, pitches and releases through both endings of the first strain. Adapt the comparators to accept importer output. Both existing checks passed against the guide adaptations during this study. Keep those expectations and add separate assertions for previously omitted markings. [Haydn comparator](../issues/197/check-edition.py) · [Haydn excerpt boundaries](../issues/198/README.md) · [Joplin comparator](../issues/199/check-joplin.py)
- **Compare equivalent encodings.** Scale XML divisions and all affected durations/offsets together, use the official timewise/partwise transforms, and wrap the same score in MXL under a different member name. In LilyPond compare absolute and relative entry, inlined and named music, explicit and inherited durations, and one-file versus virtual-include versions. Assert equal musical observations while allowing source ranges to differ. Add a changed note or tuplet ratio as a negative control that must fail comparison.
- **Inspect the score people will use.** For each feature marked supported, parse the emitted text in a fresh consumer. Exercise screen SVG/Canvas, printed part/conductor, and performed visits where applicable. Check notehead and beam group, staff assignment, lyric attachment, cross-system endpoints and TAB positions against the source PDF or native SVG. Use stable structural assertions and selected white-background crops for review. Use pixel baselines within one pinned renderer. Different engravers can legitimately space the same phrase differently. [VexTab browser runner](../scripts/test-browser.mjs) · [Edition and reading tests](../issues/200/README.md)
- **Measure failures as well as passes.** Test invalid input, ambiguous spellings, missing include, unmatched span, mixed encoding, truncated archive, and input/output/expansion limit boundaries. Generated small valid expressions should have exact rational bar sums and preserve all supported heads. Fatal cases return a located diagnostic and no misleading score. For each corpus publish counts for exact, partial, failed and out-of-profile cases, per feature and per score, with the full denominator. Count a partial fixture with a precisely expected warning as a diagnostic pass and a fidelity loss.

### Size, speed and full-score capacity

The [pinned Haydn MXL and digest](../issues/197/check-edition.py) provide a reproducible size case. Its 197,968 archive bytes expand to 4,231,200 bytes of score XML. Each of four parts has 531 measures. Counting note elements without a chord-continuation or grace child yields 10,014 timed note/rest records before any emitted skips. The full file crosses the current 4,096-event limit under direct event-for-event translation. Keep both the repository excerpt and the complete archive in the benchmark manifest. Report exactly which one a test converted.

Use one fixed Node runner and a named browser/worker runner. Measure cold module load, decode/inflate, read and resolve, write, optional source maps, and public reparse separately. Report median and p95 wall time, events/second, peak Node RSS above baseline, browser worker timings and output bytes. Include a melody, a 32-bar two-voice piece, the quartet, dense piano and a repeated-variable LilyPond score. Double bars and voices separately to detect repeated scans. Use indexed lookups for span endpoints and append/join output. For larger scores, process and release per-part or per-measure structures as soon as their unresolved references allow. Offer worker cancellation and input/work limits.

Set a hard gate of **zero importer modules or bytes** in the ordinary VexTab production graph. Each format-only browser entry must exclude the other reader, ZIP loads only for MXL, and all conversion entries must exclude VexFlow, fonts, DOM shims and native tools. Check bundler metadata as well as minified/gzip entry and chunk sizes. In M0 record the Node version, hardware, corpus hashes and timing distribution. Use that baseline to set per-entry byte ceilings and absolute time budgets for interactive and large-file conversion. Treat a reproducible regression above 15% in p95 time or peak RSS on the same runner as requiring investigation.

The first public preview can follow M2A or M2B independently with its format and feature profile named. For a production release, require an editable full piece from each advertised format, verified written and performed observations, and a published account of any remaining losses. That makes the release decision depend on music that users can actually open and edit.
